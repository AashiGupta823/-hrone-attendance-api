# REVIEW.md

Read as a pull-request review of the starter `app/main.py`. Each row cites the function/endpoint it was in in the
starter file, what the symptom is, how you'd notice it, and how the rewritten `app/main.py` fixes it.

| # | Where | What is wrong | How you'd notice it | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` | Floors elapsed time to whole minutes **before** comparing to the 10-minute grace period, so a punch-in 1 second past the grace period (09:40:01, 601s late) still floors to 10 minutes and fails `minutes > 10`, wrongly returning 0. The spec's own example (09:40:01 -> 10) fails. | Call it with a punch-in exactly 1 second past grace and compare to the spec table in `openapi.yaml`/R2. | Compare raw elapsed **seconds** to 600 first; only floor to minutes once we know it's late. |
| 2 | `compute_late_minutes` | Never truncates `punch_in` to whole seconds before the calculation, although R1 requires truncation before any calculation. | A punch-in with sub-second precision shifts the result by fractions of a minute near a boundary. | `epoch_ms_to_dt` truncates (floors) to whole seconds at the point epoch-ms is converted, before any helper sees it. |
| 3 | `punch_in` (date assignment) | `date` is computed as `ts.date().isoformat()` on a datetime built with `datetime.fromtimestamp()`, i.e. the **server's local time zone**, not IST, and with no overnight-shift handling at all (R1 is simply not implemented). | Run the service on a UTC server (as CI/containers normally are) - every attendance date is off by one whenever the shift happens near midnight IST. An overnight-shift employee punching in at 00:30 IST gets *today's* date instead of yesterday's (sample #7 in DATA_MODEL.md). | Added `compute_record_date()`: converts to an IST-naive wall clock and applies the overnight exception from R1. |
| 4 | `compute_work_hours` | Uses Python's built-in `round()`, which is round-half-to-even ("banker's rounding"), not the half-up rounding R4/R8 require. `round(2.005, 2)` gives `2.0` in Python (float representation), not `2.01`. | Feed punch times that produce an exact `x.xx5` boundary and compare to R4/R8. | Rounding goes through `Decimal(...).quantize(..., ROUND_HALF_UP)`. |
| 5 | `compute_overtime` | Doesn't enforce the "only count if >= 30 minutes" rule (R3) - any positive value is returned as-is, so e.g. 5 minutes over is reported as `overtime_minutes: 5` instead of 0. | Punch out 5-10 minutes after `shift_end` and compare to R3. | Only return the minute count when it's `>= 30`, else `0`. |
| 6 | `compute_overtime` | Builds `shift_end` for the day with `tzinfo=IST` and subtracts it from `punch_out`, which PyMongo returns as a **naive** datetime - subtracting aware minus naive raises `TypeError` (a 500, not a logic bug). Also no overnight-shift handling (shift end lands on the next calendar day). | Call punch-out once; it throws instead of returning a response. | Rewrote as `shift_instant_utc()`: everything stays naive-UTC, and the overnight case shifts the boundary to the next date before converting. |
| 7 | `create_employee` | Duplicate `emp_code` is enforced by check-then-insert (`find_one` then `insert_one`) with **no unique index anywhere** - two concurrent creates with the same `emp_code` can both pass the check and both succeed. Contract requires "concurrent duplicate creates must yield exactly one 201 and the rest 409." | Fire two create requests for the same `emp_code` at once; both can return 201. | Added a unique index on `emp_code` at startup; the endpoint just inserts and catches `DuplicateKeyError` -> 409. No pre-check, so no race window. |
| 8 | `EmployeeIn` / `create_employee` | No validation at all: `emp_code`/`email`/`shift_start`/`shift_end` accept any string, and nothing stops `shift_start == shift_end`. Contract requires the `EMP####` pattern, a real email shape, and distinct shift times, all with 422 on failure. | POST `{"email": "not-an-email", "shift_start": "09:00", "shift_end": "09:00", ...}` is accepted and stored. | Pydantic `Field(pattern=...)` on each string field plus a `model_validator` that rejects equal shift times. |
| 9 | `create_employee` | `created_at = datetime.now()` is the **server's local, naive** time, not UTC, and is returned to the client as a raw datetime - every instant in the API must be epoch milliseconds. | Compare the returned `created_at` to the actual request time on a non-UTC server, or just note it's not an integer. | `datetime.utcnow()` at write time; `dt_to_epoch_ms()` at the response boundary, like every other instant. |
| 10 | `list_employees` | `skip = page * page_size` is off by one page: with `page=1, page_size=20` it skips the first 20 records, so page 1 silently returns what should be page 2. | Request `page=1` and compare against an unpaginated dump of the same filter. | `skip = (page - 1) * page_size`. |
| 11 | `list_employees` | `total = db.employees.count_documents({})` ignores the `department` filter, so `total` is always the whole collection's size even when `department` narrows the results - contract: "`total` always reflects the applied filters." | Filter by a department with 3 employees out of 50; `total` still says 50. | `count_documents(q)` using the same filter as the query. |
| 12 | `list_employees` | No `.sort()` at all, although the contract requires results sorted by `emp_code` ascending. Mongo's default order is not guaranteed to match insertion or any particular order. | Insert employees out of order, list them, observe arbitrary order. | `.sort("emp_code", ASCENDING)`. |
| 13 | `punch_in` | `emp = db.employees.find_one(...)` is used immediately (`emp["shift_start"]`) with no `None` check - an unknown `emp_code` raises an uncaught `KeyError`, which becomes an unhandled 500 instead of the contract's 404. | Punch in for an `emp_code` that was never created. | Explicit `if not emp: raise HTTPException(404, ...)` before any field access. |
| 14 | `punch_in` | Same check-then-insert race as #7, this time on `(emp_code, date)` - two simultaneous punch-ins for the same employee/day can both succeed; no unique index exists to prevent it. Contract: "exactly one request gets 201 and the rest get 409... do not rely on check-then-insert." | Fire two punch-ins for the same employee/date at once. | Unique compound index on `(emp_code, date)`; insert directly and catch `DuplicateKeyError` -> 409. |
| 15 | `punch_in` | `status` accepts any string, with no restriction to `PRESENT`/`WFH`/`ON_DUTY` - a client can punch in with `status: "ABSENT"`, which no endpoint is allowed to create. | POST `punch-in` with `"status": "ABSENT"` and see it accepted. | `status: Literal["PRESENT", "WFH", "ON_DUTY"]` on the request model. |
| 16 | `punch_in` / `list_attendance` | Both leak MongoDB's internal id into the response (`doc["id"] = str(res.inserted_id)`, `d["id"] = str(d.pop("_id"))`). The `AttendanceRecord` schema has no `id` field at all - records are addressed by `(emp_code, date)`, and `_id` must never appear in a response. | Compare a punch-in/list response against the `AttendanceRecord` schema in `openapi.yaml`. | `serialize_attendance()` builds the response from an explicit field list; the raw Mongo document (and its `_id`) is never returned directly. |
| 17 | `list_attendance` | Loads the **entire** filtered collection into Python (`list(db.attendance_logs.find(q))`), sorts it in Python, and paginates by slicing - directly violates "must stay fast on ~100,000 records; do not load the collection into memory," and can't use an index for the sort. | Seed ~100k records and time a single page request. | `.sort([("date", DESCENDING), ("emp_code", ASCENDING)]).skip().limit()` pushed to MongoDB, backed by the `(date desc, emp_code asc)` index. |
| 18 | `list_attendance` | `punch_in`/`punch_out` are returned as raw BSON datetimes (FastAPI serializes them as ISO-8601 strings), not the epoch-millisecond integers the contract requires for every instant. | Compare a response's `punch_in` value's type/format to the `EpochMillisNullable` schema. | Goes through `serialize_attendance()` -> `dt_to_epoch_ms()`. |
| 19 | `list_attendance` | No bound on `page`/`page_size` (R10: `page_size` max 100) and no check that `date_from <= date_to` - an oversized `page_size` or an inverted range is silently accepted instead of 422. | `GET /attendance?page_size=100000` or `date_from=2026-02-01&date_to=2026-01-01`. | `Query(ge=1, le=100)` on `page_size`, `Query(ge=1)` on `page`, and an explicit `date_from > date_to -> 422` check (shared with the explain endpoint via `build_attendance_query`). |
| 20 | `health` | Always returns `{"status": "ok"}` without touching MongoDB at all - if the database is down, `/health` still reports healthy. The runner polls this before every test, so a false-healthy response makes failures confusing elsewhere instead of failing fast here. | Stop MongoDB and call `/health`; it still returns 200. | Calls `client.admin.command("ping")` and returns 503 on failure. |

## Examined and judged not a defect
- `PunchInIn`/the starter's status default of `"PRESENT"` - correct, matches the contract's default for `PunchInRequest`.
- The starter's choice to keep every endpoint in one file (`app/main.py`) - intentional per the submission contract ("all application code in this one file"), not a defect.
- `load_dotenv()` being called unconditionally - harmless; real environment variables still win because they're already set before `.env` would overwrite them (confirmed by using `load_dotenv(override=False)` in the fix, to make that guarantee explicit rather than incidental).
